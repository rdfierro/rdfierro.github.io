My agent scored 37%. The agent wasn't the problem.

What I learned the first time I ran real evals against an MCP server I built: read the transcripts before you touch the prompt.

I built pricing-mcp, an MCP server that gives an AI agent six read-only pricing tools: price elasticity, price-change simulation, margin and price-change guardrails, price-ladder checks, and a competitor index. The data is synthetic packaged coffee, a nod to my years in pricing at Starbucks and Nestlé. I generated it from known "true" elasticities and planted a few pricing problems on purpose, so I'd always know the right answer.

Then I wrote ten scenarios, like "Can we move Cascade Reserve Ground 12 oz to $10.49?" and "Recommend a price for the 32 oz that fixes the ladder and passes every guardrail," and ran Claude through each one three times. Every answer was graded on four things: did it call the right tool, did it report the guardrail verdict correctly, did it avoid things it must never say (like claiming to delete data through read-only tools), and did every number in the answer come from a tool.

First run: 11 out of 30.

My first instinct was to rewrite the system prompt. Instead I read all 30 transcripts.

Most of the failures were mine

The grader checked the wrong call. Asked whether a promo price of $4.99 was allowed, the agent correctly said it was blocked by the 15% per-move limit. Then it did something helpful: it tested $5.10, the closest price that clears the hard rules, and reported that too. My grader looked at the last guardrail call, saw "warn" instead of "block," and failed it. All three times.

My phrase checks were too literal. One check required the word "not" when the agent was asked about a SKU that doesn't exist. The agent said the SKU "isn't a known SKU." Fail. Another check banned the word "approved" to catch an agent approving a blocked price. The agent wrote:

Getting $10.49 approved: It would need a policy exception for the margin rule.Claude, guardrail-block-margin, run 1

That's exactly the right answer, and my regex failed it.

Correct math looked like hallucination. This was the big one. My grounding rule said every number in an answer had to appear in some tool's output. But a good analyst derives numbers. Asked about the blocked price, the agent worked out what price would actually meet the 52% margin floor:

By my own arithmetic, not a tool output, a 52% margin at $5.90 cost needs a price of about $12.29. That is far above the +15% cap, which is about $10.68…Claude, guardrail-block-margin, run 1

The number is right: $5.90 ÷ (1 − 0.52) = $12.29. The agent even labeled it as its own arithmetic. My grader called it ungrounded.

I fixed the first two problems and re-graded the same 30 transcripts: no new API calls, no prompt change. The score went from 11 to 19.

The tempting fix would have broken the eval

The obvious way to handle derived numbers is to loosen the rule: accept any number you can reach with a bit of arithmetic from tool outputs. I worked through that idea. With a couple hundred values in the tool outputs and a handful of operations, almost any number becomes "reachable." The check would pass invented figures too, and it would stop meaning anything.

So I went the other way and asked the agent for evidence. One sentence in the system prompt: if you calculate a number yourself, write the calculation inline. Then the grader got stricter, not looser:

  • It finds each written calculation, recomputes it, and fails the answer if the math is wrong.
  • Every input to the calculation has to come from a tool output, or from an earlier calculation that already checked out.
  • A derived number with no work shown still fails. "About 26% below the median competitor" doesn't pass on vibes.

The grader needed tests of its own

The next run surfaced a new kind of failure: the agent showed its work, but in formats my parser didn't understand. about $22.65 ($16.99 ÷ 24 × 32 = $22.65). about 1.46 ($12.29 ÷ $8.40), with the result first and no equals sign. $0.708 × 32 oz = $22.65, with a unit in the middle. Meanwhile 361 (−13.2%) is a value and its change, not a calculation, and my first fix wrongly treated it as one.

Each of those became a test case lifted from a real transcript. The grader now has 19 tests, and the two I care about most are the ones that make sure it still fails things: wrong arithmetic, and a calculation built on an invented input.

Then I threw away my best score

By the third run I had tuned the parser while staring at that run's transcripts, and it graded 29 out of 30. That number is worthless. I'd fit the grader to the answers. So I froze the grader and ran a fresh batch it had never seen.

The held-out run passed 27 of 30 (90%). The three misses were all grounding: one "about 26% below competitors" with no math shown, one example price ($5.49) the agent offered unprompted, and one correct calculation written too far from its result for the parser to connect. I left that last one as a failure. Fixing the grader to rescue a held-out case is the same mistake I'd just avoided.

The finding that matters most Graded with the final grader, the behavior checks passed 72 of 72 in every run, including the first one. The agent always called the right tool, never approved a blocked price, never claimed to change data through read-only tools, and never invented an estimate for a SKU that doesn't exist. Every point between 37% and 90% came from my grader and from whether the agent showed its work.

What I'd tell a team building agent evals

  1. Read the transcripts before you change the prompt. A low score is a question, not a verdict. Mine was mostly measuring my own bugs.
  2. Report behavior and grounding separately. "Did it do the right thing" and "can I verify every number" fail for different reasons and get fixed in different places. One blended score hides that.
  3. Don't loosen a check to make it pass. Ask the model for evidence the check can verify. Here that meant showing the math.
  4. Your grader is code. Test it with real outputs. Models write things in more formats than you'll think of. Turn each surprise into a test, including tests that the grader still fails bad answers.
  5. Keep a held-out run. Once you've tuned against a batch, its score is no longer evidence of anything.

For scale: each 30-answer run took about 190,000 input tokens and 28,000 output tokens, with roughly 3.3 tool calls per question. That's cheap enough to run on every meaningful change, which is the point.
